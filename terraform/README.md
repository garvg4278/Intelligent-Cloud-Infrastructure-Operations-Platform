# terraform/

Real AWS infrastructure-as-code for the environments the `infrastructure`
service (see `services/infrastructure/`) provisions: VPC, EKS cluster,
managed Postgres (RDS), managed Redis (ElastiCache), an S3 artifacts
bucket, and IRSA for pod-scoped AWS permissions.

```
terraform/
├── bootstrap/            # apply once by hand: creates the state bucket everything else needs
├── modules/
│   ├── network/           # VPC, subnets, IGW, NAT
│   ├── eks/                # cluster, managed node group, OIDC provider
│   ├── rds/                 # Postgres, matches docker-compose's postgres:16-alpine
│   ├── elasticache/         # Redis, matches docker-compose's redis:7-alpine
│   ├── object_storage/      # S3 bucket for artifacts
│   └── irsa/                 # generic "trust this ServiceAccount, grant this policy" IAM role
└── environments/
    ├── staging/            # cheaper choices: single NAT, spot nodes, no Multi-AZ
    └── production/         # resilient choices: NAT per AZ, on-demand nodes, Multi-AZ RDS, deletion protection
```

## Status: written, not applied

This is the same category of honesty the rest of this repo already
practices for the Helm chart and Prometheus/Grafana config (see the root
README's "Known simplifications"). To be specific about what that means
here:

- **What was done:** every `.tf` file was hand-written against the AWS
  provider's actual (v6.x, checked against current docs while writing
  this) resource schema, then checked with a structural balance script
  (`scripts/check_tf_balance.py` in this directory) that walks every file
  looking for mismatched braces/brackets/quotes -- the class of error
  `terraform validate` would catch first, that doesn't need a provider
  plugin or AWS credentials to check for.
- **What was not done, because it couldn't be from this sandbox:** no
  network egress at all was available while building this (not even to
  registry.terraform.io), so `terraform init` -- which downloads the
  actual provider plugin -- has never run. That means the deeper
  correctness checks `terraform validate` and `terraform plan` do
  (argument names against the provider's real schema, type-checking
  interpolations, whether a referenced attribute actually exists on a
  resource) have not happened. Do that, with real AWS credentials in a
  sandbox account, before trusting this against anything that costs money.

## Order of operations

```bash
# 1. Once per AWS account, with local state:
cd bootstrap && terraform init && terraform apply

# 2. Put the bucket name that created into environments/*/backend.tf,
#    replacing the "icop-terraform-state-CHANGE-ME" placeholder.

# 3. Per environment:
cd environments/staging
cp terraform.tfvars.example terraform.tfvars   # edit if your account's AZ names/region differ
terraform init
terraform plan
terraform apply

# 4. Point kubectl at the new cluster (also printed as a Terraform output):
aws eks update-kubeconfig --name icop-staging --region us-east-1

# 5. Hand off to Ansible (../ansible/) for post-provision node
#    configuration, then to GitOps (../gitops/) for deploying the ICOP
#    services themselves onto the new cluster.

# 6. Patch the real deployment_irsa_role_arn output into GitOps' values
#    (replaces a placeholder -- see terraform/modules/irsa/README.md for
#    what this does and does NOT close, especially the note on staging
#    vs. production sharing one values file):
terraform output -json | python3 ../scripts/apply_irsa_output.py
```

## Design choices worth knowing about

- **Modules take no opinion on environment; environments take no opinion
  on how a resource is built.** `modules/rds/main.tf` doesn't know
  "staging" or "production" exist -- it just exposes `multi_az`,
  `deletion_protection`, etc. as variables. Every staging-vs-production
  difference lives in `environments/*/main.tf`'s module call arguments,
  visible in one place per environment rather than scattered through
  conditionals inside shared modules.
- **Secrets never appear in a `.tf` file.** The RDS master password is
  generated by Terraform (`random_password`) and stored in Secrets
  Manager, never written to a variable default or output in plaintext --
  matching this platform's own "never store secrets in source code"
  principle (ROADMAP.md's linked design doc, section 20). `terraform plan`
  output would still show it (Terraform's own limitation, not something
  this repo's structure can fully hide), which is exactly why state
  itself lives encrypted in S3, not in this repo.
- **This provisions the platform's own infrastructure, not "an
  environment for a user's app."** The original design doc's
  Infrastructure Service section describes a more general
  environment-provisioning-as-a-product idea (ROADMAP.md's linked design
  doc, section 6.4) -- arbitrary per-user staging environments on demand.
  What's built here is narrower and more honest: the actual AWS
  infrastructure this specific platform (its 9-turned-10 services) needs
  to run somewhere real. Generalizing it into a multi-tenant
  environment-per-user product is a real, larger, separate piece of work.
