# Deployment Service

Owns the deployment lifecycle: `pending -> deploying -> health_checking ->
succeeded`, or `-> rolling_back -> rolled_back` / `failed` if the rollout's
health check doesn't pass. Talks to Helm and kubectl to actually do it.

## Endpoints

| Method | Path                    | Purpose                                      |
|--------|--------------------------|-----------------------------------------------|
| POST   | `/deployments`           | Start a deployment (202, returns immediately) |
| GET    | `/deployments/{id}`      | Current status of one deployment              |
| GET    | `/deployments`           | List, filterable by `service_name`/`environment` |
| GET    | `/health`                | Liveness                                       |
| GET    | `/metrics`               | Prometheus exposition format                   |

`POST /deployments` enqueues a Celery task and returns right away with
status `pending` (or further along, if the task already ran -- see the
eager-mode note below) rather than blocking the HTTP request for however
long a real rollout takes.

## How a deployment actually runs

1. API creates a `Deployment` row (`pending`) and enqueues
   `deployment.execute` on the `deployments` RabbitMQ queue
2. A Celery worker picks it up, marks it `deploying`, and runs
   `helm upgrade --install <service> <chart> --set image.tag=<tag> -n <env>`
3. Marks it `health_checking`, runs
   `kubectl rollout status deployment/<service> -n <env> --timeout=<t>s`
4. Rollout succeeds -> `succeeded`, and this deployment becomes the new
   rollback target for this `service_name` + `environment` pair
5. Rollout fails/times out -> `rolling_back`, runs
   `helm rollback <service> <previous-good-revision> -n <env>`, then
   `rolled_back` (or `failed` if even the rollback command fails)

## What's real vs. simulated in THIS repo's test runs

- The state machine, RBAC-style validation, rollback-targeting logic, and
  the whole API are exercised by real tests (`tests/test_api.py`) against
  a `FakeOrchestrator` standing in for a cluster, with Celery running in
  its own supported eager/synchronous test mode -- no RabbitMQ needed to
  run `pytest`.
- `HelmOrchestrator` -- the class that actually shells out to `helm` and
  `kubectl` -- has its own tests (`tests/test_orchestrator.py`) that mock
  `subprocess.run` and check the exact command lines it builds and how it
  interprets exit codes/timeouts. That's real coverage of *this code*,
  but it is **not** coverage of "does a real cluster accept these
  commands" -- there's no cluster available to test against here.
- To actually deploy something, point `docker-compose.yml`'s worker at a
  real cluster (mount a working kubeconfig) and a real chart (see
  `infra/helm/service-chart` at the repo root, which has its own honesty
  note about what is/isn't validated).

## Audit trail

Four events, covering the full lifecycle: `deployment.triggered` on
every `POST /deployments`, then exactly one of `deployment.succeeded`
(health check passed), `deployment.rolled_back` (health check failed,
automatic rollback completed), or `deployment.failed` (the deploy step
itself failed, or a rollback was attempted and *that* also failed, or an
unexpected error). All four use `actor: "system"` — this service has no
caller identity available. The gateway verifies every request's identity
now (Phase 6, see the root README), and forwards it as an `X-ICOP-User`
header — this service just doesn't read that header yet, which is a
smaller, more honest gap than "the gateway doesn't check who's calling"
was.
Nothing in the deployment lifecycle depends on the audit call
succeeding — a failure there is caught and logged, not propagated. See
`test_audit_failure_does_not_break_deployment_creation` and
`test_audit_failure_does_not_break_a_rollback` in `tests/test_api.py`.

## Known simplifications

- Real Alembic migrations now (see the auth service's README for the
  verification approach — same pattern here: autogenerated, checked
  against `create_all()`, upgrade/downgrade/re-upgrade all confirmed
  against SQLite, not verified against live Postgres specifically).
- No manual rollback endpoint yet -- rollback currently only happens
  automatically when a health check fails. `POST /deployments/{id}/rollback`
  is a reasonable next addition.
- Postgres is shared with the auth service (same instance, separate
  table) rather than a physically separate database. Fine pre-scale;
  worth splitting later.
- One chart, `service-chart`, used for every service via `--set image.repository/tag`.
  That's intentional for now (one thing to get right instead of N
  slightly-different charts) but won't fit a service with a genuinely
  different shape (a StatefulSet, say) without a second chart.

## Run standalone

```bash
pip install -r requirements.txt
export DATABASE_URL=postgresql+psycopg2://icop:icop@localhost:5432/icop
export CELERY_BROKER_URL=amqp://icop:icop@localhost:5672//
export AUDIT_SERVICE_URL=http://localhost:8008
alembic upgrade head
uvicorn app.main:app --reload --port 8000
# in another shell:
celery -A app.tasks worker --loglevel=info
```

## Test

```bash
pip install -r requirements.txt
pytest
```
